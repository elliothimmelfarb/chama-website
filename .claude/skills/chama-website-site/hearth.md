- Writing a crafted record: `add_transcript` with `draft: true` (no model, no mail), then `set_record_figure` per picture, `set_record`, `set_record_cards`. None of them email the member; the invite does.
- `add_transcript` only attaches to an existing member, and the MCP server has no way to create one. For someone not yet invited, insert the user with `createUser` from `lib/hearth/users.js` (role `client`, plus `billing` if it isn't pre-buy) through a throwaway script run from the repo root with the pulled env. No mail goes out, and the later invite finds the existing user and just sends the link.
- A long transcript is easier to send by posting JSON-RPC `tools/call` to `https://chamainteligente.com/mcp` with the `Authorization` header from the `chama-hearth` entry in `~/.claude.json` than by pasting it into a tool call.
- Elliot's way of working on a record (2026-10-19): read the transcript, then ask him one question at a time (lessons, homework, cheat sheets, figures, framing) until he says done, and only then write. Owners can open any member's record at `/hearth/transcripts/<id>`.
- Record figures render at about half size on a phone (600-unit viewBox in a ~340px column). Draw at 600 wide with body text at 17 or more and labels at 14 or more, and check them as PNGs with `qlmanage -t -s 900` before uploading.
- A browser that loaded the Hearth before a deploy keeps the old `hearth-*.js` for up to ten minutes, so a new record can render in the old layout. Fetch the assets with `cache: 'reload'` before judging.
- Billing modes (2026-10-15): every member defaults to pre-buy (`users.billing = 'prebuy'`); flip one to billed after on their member page. Bookings carry their own `billing` ('credit', 'after', 'free') so a member changing mode later does not rewrite history. Since 2026-10-30 a billed-after member sees nothing about packs, credits or paying: `GET /packs` returns none, `POST /purchases` refuses, and `/sessions/packs` sends them to `/sessions`. Their invoices still show.
- To see the Hearth with data locally without touching production, run the real `handleHearth` against PGlite (`@electric-sql/pglite` installed in the scratchpad, never in the repo), apply `MIGRATIONS` statement by statement, seed users and `login_sessions` rows with `hashToken("tok-...")`, and set the `__Host-chama_hearth` cookie in the browser. Chrome accepts `Secure` cookies on `http://localhost`. PGlite returns `Date` objects where Neon returns strings; convert them to ISO strings in the adapter.
- In the availability grid, cell heights must be whole pixels. Fractional heights (1.05rem) leave visible seams inside painted blocks.

- The Hearth's `GOOGLE_CLIENT_SECRET` is Sensitive, so a pulled env cannot get a Google token locally. To see raw Google data for the Chama account, use the `chama-google` MCP server's own Keychain token: `uv run --directory ~/code/chama-google-mcp python` with `chama_google_mcp.auth.session()`.

- The painted week's cells can sit at fractional pixel offsets (anything above them with a fractional height moves them), and then adjacent painted cells show anti-aliased seams. Each painted cell carries a 1px ember shadow downward to cover them; whole-pixel cell heights alone were not enough.
- Stripe (2026-10-15): the Stripe account (`acct_1ULK5fKIjHJB7Aop`, live only, no sandbox) is shared with ShopIntake. - To click through card checkout locally, have the stubbed `api.stripe.com` return a session `url` on a fake https host and fulfil it in Playwright with `page.route(/checkout\.stripe\.test/, ...)` as a 302 to a local fake page whose Pay link marks the session paid and redirects to `success_url` (rewritten to http). The room follows only `https://` checkout URLs, so an http fake URL fails with "Card payment is not working".
- The Stripe MCP connector can create customers, invoices and webhook endpoints but cannot delete anything (no `Delete*` operations). A webhook endpoint's signing secret is only returned on create, so pipe it straight into `vercel env add` and the Keychain (`chama-hearth-stripe-webhook-secret`).

- To click through invoices locally, the PGlite harness can stub `globalThis.fetch` for `api.stripe.com` and serve a fake hosted page whose Pay button posts a signed `invoice.paid` to `handleStripeWebhook`.
- Guests have no `sessions.own`, so they cannot open Sessions or the packs page; that is why `GET /invoices` needs only a signed-in person and an open invoice shows on Home.
- Wide screens (2026-10-15, redone 2026-10-30): the room no longer sits in a centred `--col` strip. The bar and shell run edge to edge, the nav is pinned left, and `.hh-view` is capped at `--content` (76, 84, 92rem as the screen grows) and centred in what is left. The flame canvas must hang from `.hh-mast`, not the inner `.frame`, or its left edge shows as a hard seam on wide screens; its mask fades at a fixed rem distance so the glow stays brand-sized. The root font grows to 17 and 18px at 112 and 150rem; those `html { font-size }` rules must come after the base `html` rule, or the base 16px wins. Long reading uses `.reading`, capped at `--read`. SVG figures that scale with width (metrics charts, the sessions hops) need a grid or a `max-height`, or they balloon on a wide column. The PGlite harness plus Playwright's cached `chromium_headless_shell` (`executablePath`) screenshots several widths in one run; sign in through a harness `/login/<token>` route, since `addCookies` rejects `__Host-` cookies on http. The harness needs `@electric-sql/pglite` freshly installed in the scratchpad (copied `node_modules` from old scratchpads come back incomplete) and a free port (4991 is often taken by another session).
- Availability by date (2026-10-22): hours live in `availability_days` with `day` as `YYYY-MM-DD` text, not a `date` column, because node-postgres style drivers turn a `date` into a midnight instant in the server's zone and shift it a day. `PUT /admin/availability` rewrites only the dates it names. The MCP `available_slots` tool now uses the same `slotsFor` as members; before, it ignored openings and Google busy time. Migration 010's 60-day backfill made every future week look painted, which read as "setting this week sets all weeks"; 011 removed the exact template copies from 2026-11-09 on. Seeding future data from a template hides that the model changed, so prefer a short backfill.
- The PGlite harness can test a data migration: run migrations below the new id, seed the old rows, then run the rest.
- The public page (2026-10-22): `/hearth` is chosen by cookie in `vercel.json` (`has` / `missing` on `__Host-chama_hearth`), because LinkedIn would not save a link to a `noindex` page. There must be no `hearth.html` at the root, or the static file would be served before the rewrites. `vercel dev` ignores `has`, so it always shows the public page; test the room side on a preview with `curl -H "Cookie: __Host-chama_hearth=x"`. `robots.txt` disallows `/hearth/` (with the slash), not `/hearth`, or crawlers that honour it (LinkedInBot does) skip the page.
