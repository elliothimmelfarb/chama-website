The Hearth.
The website becomes the company.

Designed by Fable, owned end to end.
Tracking: issue #29
Status: building, milestone A in progress

A hearth is the place in a house where the fire is kept and people gather around it. Chama Inteligente already has the fire, the intelligent flame on the homepage. The Hearth is the room around it: where clients keep everything from their work with Elliot, where members run the business, and where their agents can come and sit too.

1

For a client

Buy a pack of sessions, book them against Elliot's real availability, and own every transcript. Each session comes back as a summary, the key points, the decisions, and follow-ups for both sides. Ask the flame about your own sessions. Point your Claude at it and it knows what you two talked about.

2

For Elliot

Members and roles, packs and prices set in the room rather than in code, availability, the transcript intake, metrics, an audit log of who came, went and what their agents called. The existing flame admin folds in as one section.

3

For an agent

An MCP server on the company's own domain. OAuth 2.1 with dynamic registration and PKCE, so "add custom connector" in Claude just works; API keys for scripts and other agents; a public read-only tool set for anyone's assistant. The company that teaches organizations to be callable is callable.

What you did not ask for and, I think, want

The things that make it "I would tell people about this"

Your sessions, drawn

The homepage already has the figure: sessions as hops that reach a little further each time. A client's home page in the Hearth is that figure, drawn from their real sessions, growing as they go. Nobody else's dashboard is the company's own homepage metaphor made personal.

Ask the flame about your sessions

The same flame from the homepage, in the client's room, with only their own transcripts as context. "What did we decide about the sales pipeline in July?" A private, personal intelligent flame. Transcripts are data, never instruction, same rule as everywhere on the domain.

Follow-ups that live between sessions

Derived follow-ups become a shared list with an owner (you or them) and a due date. The client's agent can read and tick them. The next session opens with what happened since, not "where were we".

Before-next-time

A short "try this before we meet" block derived from each transcript, so the doing between sessions (the mechanism the offer names for how skills compound) has a place to be written down and reported on.

A fatura-shaped purchase flow

Portugal requires invoices from certified software, so Stripe alone was never going to be the whole flow. Purchase requests land in your room, you issue the fatura from the certified software, mark it paid, and credits appear. A Stripe adapter can be switched on later behind the same interface without touching the rest.

The organization, queryable

The public MCP tools are the demo you cannot give today: a prospect points their assistant at chamainteligente.com during the meeting and it comes back with the brief, the offer in structured form, and how to get in touch. Bold proposal B from the domain-unlocks page, built.

Every event, one log

Sign-ins, sign-outs, bookings, purchases, transcript uploads, every MCP call with its tool name, every API key use: one append-only audit log with the actor, the country and the device family, never the IP. The metrics page reads from it.

Referral rewards you can change

Every member has a referral link. When a referred person's first pack is paid, the referrer gets the reward you configured: a free session credit or a percentage off their next pack. The rule lives in settings, not in code.

Passkeys next

Sign-in is built so passkeys (WebAuthn) can be added as a second factor or a primary key in the next milestone. That is the world that is coming; the table for it is in the first schema.

Architecture

One room, one router, one database, one log

Why Postgres now

Blob was right for transcripts of anonymous chats. Users, sessions with revocation, a credit ledger, bookings that must not double-book, and an audit log people will query all want a real database. Neon on the Vercel Marketplace, free tier, Frankfurt, connected through Vercel's managed variables so no credential touches this repo.

Why no framework

The site is vanilla and no-build, and it is part of the story it tells. The Hearth follows: one router function, a few libraries of our own, an SPA with no dependencies. Every value from the API reaches the page through textContent.

Migrations that apply themselves

Schema versions live in the repo as SQL strings; on a cold start the router takes an advisory lock and applies any it has not yet applied. No migration command, no credential on a laptop.

Security

The design, in the order an attacker would meet it

Sign-in

  • Google: the existing ID-token flow, verified server-side against Google's keys (signature, issuer, audience, expiry, email_verified). No client secret exists.
  • GitHub, Discord: authorization-code flow with a state nonce bound to the browser and a verified primary email required. Secrets live only in Vercel.
  • Email: password (scrypt, per-user salt, minimum 12 characters, checked against a breach list of the most common passwords) with verification before first sign-in, or a magic link that is single-use and expires in 15 minutes.
  • Rate limits: per-address and per-account counters on every auth endpoint, with the same generic failure message whatever failed.

Sessions

  • Opaque 256-bit token, HttpOnly; Secure; SameSite=Lax; Path=/, 30 days sliding, hash stored. Sign out anywhere, or everywhere.
  • Every mutation checks the Origin header against the host, as the flame already does.
  • Role and permissions are read from the database on every request, so a demotion is immediate.

Agents

  • OAuth 2.1 only: PKCE S256 required, exact redirect-URI match, 10-minute codes, short access tokens with rotating refresh tokens, consent screen inside the Hearth listing the scopes in plain words.
  • API keys carry scopes and an optional expiry; a key can never do more than its owner.
  • Every tool call is logged with the actor and the tool. The metrics page shows MCP use per member per day.
  • Nothing an agent submits is instruction. Notes, follow-ups, and transcripts are stored as data a human reads, and the tool descriptions say so.

Everything else

  • Per-path CSP: the Hearth opens accounts.google.com only; the homepage promise is untouched.
  • No innerHTML anywhere in the app. No IP addresses stored anywhere. Country and device family only, for the log.
  • The owner role is protected from lockout; the first owner is whoever is on ADMIN_EMAILS.
  • Privacy notice extended with a members section before the first client signs up.

Agent-native

The MCP server

At https://chamainteligente.com/mcp, Streamable HTTP transport, JSON-RPC 2.0, with /.well-known/oauth-protected-resource and /.well-known/oauth-authorization-server so a client discovers the flow on its own. Tools appear according to who is calling.

Design language

Familiar enough to use, different enough to remember

The room is dark, the pages are paper

The Hearth is the flame room from the homepage: the obsidian ground, the ember. Long-form reading (transcripts, summaries) flips to a paper sheet laid on the dark ground. Two worlds the site already has, now with jobs.

The fire is real

The existing particle engine burns quietly in the Hearth's masthead, dimmed. It brightens for a moment when something good happens: a booking made, a transcript arriving, a follow-up done.

Figures, not widgets

Sessions as the hop line. Credits as a ring of embers that go out one by one. The audit log as a timeline. The same draw-in motion system the homepage figures use, so the whole domain moves the same way.

Mobile first, keyboard aware

Bottom navigation on phones, the composer pinned above the soft keyboard the way the flame already does it, every list scrollable in its own container, every action reachable with a thumb.

Members, top right

On the homepage masthead: "Members". Signed out it is a word; signed in it is the person's initial in an ember ring. The gate offers the four ways in, plainly, no marketing.

Quiet motion

Page changes slide and settle; numbers count up once; nothing loops except the fire. Reduced motion respected everywhere, as on the homepage.

What needs your hand

Three things only you can do, and one decision

1. Provision the database (one command, free tier, Frankfurt). The permission classifier stopped me from creating a resource on your Vercel account. Run this from the website folder; it connects the database to the project and Vercel manages the connection string, so nothing lands in the repo:
cd /Users/elliothimmelfarb/claude/chama-website && vercel integration add neon -m region=fra1 -m auth=false --plan free_v3 -n chama-hearth --no-env-pull --no-claim
2. Two OAuth apps, created in your browser (I can drive it with Claude in Chrome when you say go). GitHub: Settings → Developer settings → OAuth Apps, callback https://chamainteligente.com/api/hearth/auth/github/callback. Discord: Developer Portal → New application → OAuth2, redirect https://chamainteligente.com/api/hearth/auth/discord/callback. The client IDs and secrets go into Vercel as GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET, DISCORD_CLIENT_ID, DISCORD_CLIENT_SECRET. Email and Google sign-in work without them; GitHub and Discord buttons appear the moment the variables exist.
3. Two new secrets in Vercel. HEARTH_SESSION_SECRET (32+ bytes hex) and, for magic links and password resets, nothing new: Resend is already there. I will add the session secret with vercel env add if the classifier allows it, and tell you if it does not.
4. Google Meet (added on your request the same day). In the Google Cloud project that holds the existing OAuth client: enable the Google Calendar API and the Google Meet REST API, add https://chamainteligente.com/api/hearth/google/callback as an authorized redirect URI, add the scopes calendar.events and meetings.space.readonly to the consent screen, and put the client secret in Vercel as GOOGLE_CLIENT_SECRET. Then press Connect Google in the Hearth's Settings. From then on every booking is a Meet room on your calendar and the transcript is pulled after the meeting. In Workspace admin, set Meet transcription to automatic so nobody has to remember to turn it on.
Decision: the referral reward default. I am shipping it configurable with the default one free session credit to the referrer when the referred person's first pack is paid. Percent-off-next-pack is the other option and is a toggle in settings. Say the word if you want a different default.
