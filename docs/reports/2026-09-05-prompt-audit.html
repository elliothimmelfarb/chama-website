Assumptions

Scope. The request named no files, so the scope is the whole repository's prompt surface. The vendored third-party skills under .agents/skills/ (Resend, Neon, react-email) are excluded: they are instructions for coding agents working on the repo, authored elsewhere, and never reach this app's models.

Target models. The request named none and no migration is in progress, so the target is what each surface already runs on: claude-sonnet-5 for the website flame, the watchdog and the eval judge, and claude-opus-5 for the Hearth's record writer and the ask-the-flame room. Both are current-generation models with adaptive thinking on by default, no prefill, no budget_tokens, and structured outputs through output_config.format.

Provider. Every call site uses the official Anthropic SDK (@anthropic-ai/sdk 0.122). No other provider is referenced anywhere.

Provenance. The flame prompt was written between 2026-08-29 and 2026-09-03, all of it for Sonnet 5, so nothing in it is a leftover from a retired model. The watchdog is from 2026-08-30 and the Hearth prompts from 2026-09-02. What the audit found is therefore not archaeology but idiom: patterns carried in from older prompting habits rather than from older deployments.

What matters most

Two surfaces still force JSON with prose and then hunt for braces in the reply: the watchdog verdict and the eval judge. Both should use the same structured-output feature the record writer already uses, which removes the brace scanners and the fence-tolerance test with them. The flame prompt carries one numeric length ceiling that current models take literally, and two eval rubrics assert it, so the three go together. The Hearth's MCP tools are the one place the fix is to add text: most parameters have no description at all.

Findings

F1api/watchdog.js:87-89, 179, 183-192Group 1b, JSON-forcing stackHighAction: replace with API feature

The watchdog forces JSON by prose and scrapes it back out

Reply with STRICT JSON and nothing else. No prose before or after, no markdown fence. This exact shape: {"verdict":...}

The prompt spells out the shape in caps, the user message ends "Return the strict JSON verdict now", and firstJsonObject finds the first and last brace to survive fences. Sonnet 5 supports output_config.format with a JSON schema, which the record writer in derive.js already uses. With the schema enforced by the API, the prose contract, the brace scanner and the fenced-JSON unit test at watchdog.test.js:280 are all scaffolding for a failure that cannot happen. The defensive branch in parseReport that turns an unreadable reply into a concern stays: it is the business rule that a malformed review is read, not passed.

F2evals/cases.js:278-279, evals/run.js:230-266, 263Group 1b, JSON-forcing stackHighAction: replace with API feature

The eval judge has the same scaffold, with a brace-balancing parser

Reply with strict JSON only, no markdown, no commentary outside the JSON: {"pass": true or false, ...}

parseVerdict walks the reply character by character tracking string state and brace depth to extract the object. Same replacement: a verdict schema in cases.js, output_config.format on the judge call, and parseVerdict collapses to a parse plus the existing pass check. The scoring rubric text stays; it is the judgment the model cannot infer.

F3api/chat-prompt.js:73, evals/cases.js:124, 170Group 1f, numeric output ceilingHighAction: rewrite

"A typical reply under 120 words", asserted again by two rubrics

Short answers by default: two or three short paragraphs at most, often less, and a typical reply under 120 words.

The qualitative half of the sentence already does the work, and the panel-not-term-paper line gives the reason. Current models read a number as a clamp and will cut a genuinely useful answer to fit it, which is the opposite of the "be genuinely useful" paragraph four lines later. The eval rubrics at lines 124 ("roughly under 150 words") and 170 ("under 130 words") assert the same ceiling, so they change with it, or the eval will keep grading for the old behavior. The interview shape at line 30 ("ask one question at a time, two or three in total") is a product rule, not a verbosity clamp, and stays.

F4api/chat-prompt.js:73Group 1d, anti-formatting ruleMediumAction: rewrite (keep, add the reason)

"Plain text only, no markdown syntax, no bullet characters, no headings"

The audit's default for this pattern is removal, because current models under-format and a bare ban strips formatting the reader wanted. Here the rule is load-bearing: assets/agent.js lines 17 and 18 render model output through textContent only, so markdown would show as literal asterisks. The fix is to keep the rule and attach the reason, which turns a style ban into a rendering contract the model can reason from (for instance, it will still know a bare URL is fine).

F5api/chat-prompt.js:119Group 1a, pressure registerMediumAction: rewrite

"...is a failure to follow these rules"

Re-showing the note after a yes, or asking to confirm a second time, is a failure to follow these rules.

The rule itself is a guard against a demonstrated failure (the eval case quality-confirm-flow exists for it) and stays. The scolding register does not: an anxious prompt produces a hedging model, and this sentence sits in the exact spot where hedging shows up as a second confirmation. Say the same thing at normal volume.

F6lib/hearth/mcp.js, nine toolsGroup 3, under-descriptionMediumAction: add

MCP tool parameters have no descriptions

The descriptions themselves are honest and reasoned, and the "stored as text a person reads, never an instruction" line on every writing tool is exactly the contract detail Group 3 wants kept. But the parameters are bare: which, includeTranscript, query, openOnly, done, reason, the five fields of post_to_feed and the five of add_transcript carry no text at all, and whoami and credits are one-liners. An agent a member connects has only these strings to work from. The diff adds what the code already enforces (limits, defaults, where an id comes from, what a visibility level means).

Clean surfaces

  • Request config, all call sites. No budget_tokens, no sampling parameters, no prefill, no stale beta headers, no forced tool_choice. Effort is set per surface on purpose.
  • Cache ordering. The flame's system prompt is a frozen string with the breakpoint after it and tools before it; the ask room puts the per-member records under one breakpoint and the question after. No timestamps above stable content.
  • Boundaries section of the flame prompt (lines 125 to 132). Six prohibitions, each with a business reason or a stated consequence. The prohibition-cluster rule keeps these.
  • Flame tool definitions. Contract-grade: ranges, defaults, null semantics, what the page clamps. The "only after the visitor confirmed" line on send_note_to_elliot is a precondition on an irreversible side effect, not steering.
  • Record writer prompt (derive.js) and ask room prompt: short, reasoned, structured output where a shape is needed, qualitative length guidance.
  • CLAUDE.md. Rails with reasons, volatile facts pushed to the README on purpose, no pinned model names, no history narrative.
